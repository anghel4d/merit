## II. SYSTEM SPECIFICATION
*(source: Vindex sandyx 2026-07-17.md)*

### Overview
The centre of the system is the judgement module. Judgements are called repeatedly in conducting tasks and allowing new users to enter.

Two possible 'incentive structures' exist; merit points (M), determining status within the Vindex (determined by IQ+completion of tasks+*staking*); and value tokens (V), which could be either existing cryptocurrencies or a fiat/crypto peg, issued to new users, *tasks, and judgement pots*, that pays out WWW.

The system stores the ID, IQ, M/V, and taken-up and completed tasks of users.

### Judgements
- Judgement pot is opened (*with a small amount of M/V*). A time limit starts.
- Users stake a fixed amount of M/V into the pot to make a yes/no vote. (*Users with higher M can stake more.*) (*Users can pass their voting rights on to other trusted users.*) (*Only a randomly selected jury of users votes*.)
- When the time limit completes, or all users have voted, the majority wins.
- The pot is divided out among the winners *according to how much M they staked.*

**This is the Schelling point incentive used by Kleros to discourage biased voting.**

### Tasks
- A user proposes a task and M reward. (*External authority proposes a task and M/V reward*.)
- A judgement is called on whether the task should be accepted. The proposer makes a larger stake, which increases their payout if they win the judgement. (*But need not increase their voting power*.)
- (*If the task is accepted, any user can submit a judgement to have them alone take it up; or an M/V-based prediction market determines which user takes it up; or any user can take up a task at will*.) (*The taking-up goes on the user's record.*)
- A user who has taken up the task calls a judgement on whether they have completed it.
- If the judgement is positive, they gain the M/*V* reward and the completion goes on their record.

### Entry
- New users are tested for IQ.
- A judgement is called on whether the test was fair and the baseline entry IQ proportionate.
- If the judgement is positive, a new user is created with M proportional to their test results.

### Defects
I think Meritocracy assumes both an external authority (Benefactor is not just the user with highest M) and a means to replace it. Apart from the option of making this replacement an ordinary judgement, this model does not furnish such a means.

## III. BUILD PLAN
*(source: Building Vindex sandyx 2026-07-17.md)*

### Blockchains
As building a new client from scratch with a new privacy scheme is awkward, Claude suggests configuring/extending an existing framework, probably Hyperledger Fabric. Reasons:
- **Channels** are a natural fit for the "non-user can't see anything" requirement — the whole user network operates as one private channel; there's no public-facing channel at all.
- **Private data collections** could further restrict _who within the channel_ sees a given juror's individual vote (as opposed to just the aggregate outcome), which helps prevent retaliation against jurors who vote unpopularly.
- **Chaincode-as-endorsement-policy** is where most of your actual engineering effort goes — the reputation math, the VRF-based jury sampling, and the vote-tallying logic are all custom Go/JS/Java chaincode, not off-the-shelf Fabric behavior.

### Building process
Mechanism design > chaincode build (logic) > reputation and privacy layer
- **Mechanism design** happens mostly on paper/spreadsheets... Simulate the reputation formula and jury-weighting scheme against adversarial strategies (sybil clusters, vote-buying, collusion rings) using something like agent-based modeling.
- Chaincode build... Fabric supports Go, Node.js/TypeScript, and Java for chaincode. In practice, Go has become the de facto standard for chaincode development... If you do go with Node.js, the fabric-chaincode-node project strongly recommends using lock files for production deployments, and dependency hygiene matters more generally — a compromised or buggy npm package in your chaincode's dependency tree is a real risk vector.

(Go isn't strikingly dissimilar to Python/JS, it's statically typed + has quite efficient coroutines.)
- **Reputation and privacy layer** is where the harder engineering lives — private data collections, deciding what's threshold-encrypted vs. simply access-restricted by channel membership, and building the jury-sampling logic (ideally with a verifiable random function so sampling can't be gamed by anyone, including insiders).

(Claude assuming the random jury system here)

### Testing
Single-organisation dev network > multi-org testnet > external security audit (unlikely unless someone knows a trusted expert in this field) > pilot and expand
- **Multi-org testnet**... spin up several organizations representing different "worker factions" and actively try to break your own mechanism — bribe jurors, collude on admissions, spam low-value tasks to farm reputation.
- **Security audit** should cover both the traditional smart-contract surface (reentrancy-style bugs, integer overflow in payout math) and the game-theoretic surface (can the voting/reputation math be gamed even if the code is bug-free) — these require different expertise, so budget for both a code auditor and someone who reviews mechanism design specifically.

### Development tools
- **`fabric-samples` test network** — the standard starting point; a scripted 2-org network you bring up/down with shell scripts. Good for the first few weeks of chaincode logic development.
- **Minifabric or ChainLaunch** — faster iteration loops than the raw test network scripts, useful once you're doing rapid edit-deploy-test cycles on task/escrow/reputation logic.
- **VS Code + the IBM Blockchain Platform extension** (or equivalent) — chaincode scaffolding, packaging, and one-click install/approve/commit against a local network, if you want an IDE-integrated workflow rather than CLI scripting. [Note: this extension was confirmed defunct, unpublished Jan 2022, repository archived Jan 2023.]
- **Docker Compose** underlies all of the above — Fabric peers, orderers, and CouchDB run as containers, so a working Docker setup is a hard prerequisite regardless of which tool wraps it.

### Communications
I suggest a communications system be adopted with distinct channels where users can state what time they will be online; recieve orders from @Mykka; discuss Vindex-related topics; discuss the programming of the Vindex specifically; discuss other projects; fileshare; and spin off small groups to work on specific tasks.

## IV. CHAINCODE DEVELOPMENT LOG
*(source: Chaincode development sandyx 2026-07-18.md)*
Assumes use of Bash on Linux. Note the pivot from Fabric (§III) to Besu.

### Install Besu
Prerequisite is JDK 25+ (`java --version` > `sudo apt-get purge openjdk-\*` + `sudo apt-get install openjdk-25-jdk`)

`curl -L https://github.com/besu-eth/besu/releases/download/26.7.0/besu-26.7.0.tar.gz | tar -xz`

`export PATH=/home/[your username]/besu-26.7.0/bin:$PATH` < adds to PATH for one session. To make it permanent: `vi .bashrc`; press `i` to insert; type out the above line somewhere convenient (pipx had put a similar export line in on mine and I added it there); press `esc`; `:wq` to write to file.

### Create dev-mode network
`besu --network=dev --rpc-http-enabled --data-path=/tmp/besu-dev`

### Set up a Hardhat project
Prerequisite is node.js 22 or later.
- Hardhat is the standard tool for compiling, testing, and deploying Solidity contracts — think of it as the Node.js-ecosystem equivalent of a build tool + local test framework, purpose-built for Ethereum-style development.

`mkdir user-dao && cd user-dao`
`npm init -y`
`npm install --save-dev hardhat`
`npx hardhat --init`

The .sol contracts now live in /user-dao/contracts.

### Sample contract
- Since your end goal is a task/reward system, let's start with the simplest possible piece of that idea... just "store a task and let someone mark it done":

```solidity
// contracts/Task.sol
// SPDX-License-Identifier: MIT
pragma solidity ^0.8.20;

contract Task {
// A public state variable — its value lives permanently on the blockchain
string public description;
bool public isComplete;
address public creator;   // the account that created the task

// The constructor runs once, when the contract is deployed
constructor(string memory _description) {
	description = _description;
	creator = msg.sender; // msg.sender = whoever sent this transaction
	isComplete = false;
}

// A function anyone can call to mark the task done
function markComplete() public {
	isComplete = true;
}
}
```

- **`pragma solidity ^0.8.20;`** — declares which compiler version this code targets. The `^` means "0.8.20 or a compatible later 0.8.x version."
- **State variables** (`description`, `isComplete`, `creator`) — these aren't like normal program variables; every change to them is a permanent, recorded transaction on the ledger. Reading them is free; writing to them costs gas (even at zero gas price on your dev network, every write is still its own mined transaction).
- **`public`** on a variable automatically generates a free "getter" function, so `description` is readable from outside without you writing a `getDescription()` function yourself.
- **`msg.sender`** — a special global variable giving you the address that called the current function. This is how Solidity contracts know "who" is interacting with them — there's no login system, your wallet address _is_ your identity.
- **`constructor`** — runs exactly once, at deployment time, and never again.

### Compile contract
Delete existing contracts in /user-dao/projects.
`cd user-dao`
`npx hardhat compile`
- You should see `Compiled 1 Solidity file`... This produces an **ABI** (a JSON description of the contract's functions — how other code talks to it) and **bytecode** (the actual compiled program) in an `artifacts/` folder.

### Gas and validators (Q&A)

**Q: will gas price be minimal (so users aren't discouraged from engaging in judgements) and if so how?**
- Since this is a private network you control, you're not competing with anyone else's transactions for block space, so there's no reason to charge gas at all.
- **Who pays for the infrastructure, then?** Nobody pays _per-transaction_ — but someone still bears the real-world cost of running the validator nodes themselves (the servers). This is worth being explicit about with users: "free gas" means users never pay to participate, not that the network runs for free. That cost falls on whoever operates the validating infrastructure — which ties back to the earlier point about avoiding a small trusted operator set for exactly that infrastructure.

**Q: Would every user run a validator node, or only a few? Could a validator node be run off an ordinary laptop? Would a real-world cost be implied?**
- **Would every user run a validator?**
- Almost certainly not, for a structural reason rather than a policy choice: **BFT-style consensus protocols like QBFT don't scale well to large validator sets.** Each round of consensus requires validators to exchange messages with every other validator (proposal → prepare → commit, as we walked through with PBFT earlier), and that communication overhead grows roughly quadratically with the number of validators. In practice, most QBFT/IBFT networks run somewhere in the range of 4 to ~25 validators — beyond that, block times and finality start to degrade noticeably.
- The good news is Besu's account model still decouples _governance participation_ (proposing tasks, voting in juries, holding reputation) from _validating_: a user can do all of the former with nothing but a keypair and access to someone's RPC endpoint. Only the smaller validator subset needs to run actual node infrastructure.
- A natural design move, given your earlier admission/judgement mechanism: **let the users elect their validator set the same way it elects admissions** — a reputation-weighted vote for who runs infrastructure, term-limited or rotating periodically. That... avoids a fixed group permanently controlling the network (the same centralization risk we flagged with Fabric's org model).
- **Could a validator run on an ordinary laptop?**
- A reasonably modern laptop's CPU/RAM/disk would handle it fine computationally... the real problem is **liveness, not compute.**
- **Is there a real-world cost?**
- realistically in the tens of dollars per month range... Compare this to a _regular_ user (proposing tasks, voting, getting paid): **zero infrastructure cost**.

**Q: Would it be possible for collusion between the validators to bias the system?**
- A validator can't forge another user's signature, invent a vote that was never cast, or make the contract compute a result other than what the code and included transactions actually produce... A colluding block-proposer (or majority) can simply refuse to include a specific user's transaction... a validator could subtly delay including a legitimate last-minute vote until just after a cutoff... if colluding validators cross the fault threshold, they can stall block production entirely.

(QBFT fault threshold is (n-1)/3)

- **Mitigations**
- commit-reveal voting... if a validator can't see _how_ a user voted until after the deadline (only that a submission was made), they can't selectively censor based on vote direction.
- Let every user run a plain full node (not a validator, just a verifier) — this costs far less than validating, requires no signing key, and gives the whole community an independent way to audit whether the validator set is including transactions honestly.
- Rotate and re-elect validators frequently
- a documented process for the users to vote out a validator given evidence of censorship
